# Tracker behavior and API

Tracker owns its SQLite database and authenticated HTTP API. Farm MCP is the agent
interface; it cannot open the database. Farm API supplies identity, service tokens
and live entitlement. An authorized caller can access all Tracker lists. Stable
Farm user/client IDs are recorded in history and do not restrict individual lists.

## Lists, items and history

List names are unique without case distinction. Each item belongs to one list and
can move between lists. List names and item titles are limited to 200 characters;
descriptions to 4,000. New databases are empty; examples such as Personal, Work and
Noiseflood are not automatically created.

Item statuses are `open`, `in_progress`, `blocked`, `completed` and `cancelled`.
Cancelled records are retained and excluded from active queries. List status is
`active` or `cancelled`; cancelling a list cancels its active items and recurring
series atomically, while completed items remain completed. Restoring a list does
not restore its children automatically. No operation permanently deletes records.

Created, updated, completed and cancelled times are generated by the server in
UTC. Reopening clears the current completion timestamp while retaining the earlier
completion in append-only history. History includes user/client IDs, timestamps,
action and changed values. Scheduler events identify the Tracker scheduler.

`blocked_by` holds other item IDs, including across lists. Self references,
missing IDs, duplicates and cycles are rejected. Items with unresolved blockers
must remain blocked; complete the blockers or explicitly clear the references
before opening, starting or completing the dependent item. Cancelled blockers
are unresolved. Finishing a blocker does not automatically change the dependent
item's status, so the agent can review remaining non-task reasons for blocking.

Every mutation uses a transaction. Updates require the current integer
`expected_revision`; stale edits return `revision_conflict`. Creates and skips
require a stable `idempotency_key`, scoped to the caller and operation. An exact
retry returns the original receipt; changed input with that key conflicts. JSON
object-key ordering does not affect this comparison. Reads never write records.

## Extra data

Each item supports any number of independently editable labeled detail records.
Kinds are `text` and `json`; JSON supports objects, arrays and scalar values.
Each value is limited to 16 KiB, and pages are bounded to keep MCP responses
usable. Add more records for additional data; there is no total record-count cap.
Cancelling a detail retains it and its history. Detail changes have independent
revisions and also appear in the parent item's history.

Creation can include up to 50 initial details, totaling 32 KiB. Recurrence templates
use the same aggregate limit. Subsequent individual detail additions are unbounded
in count. Binary files and arbitrary filesystem paths are not supported.

## Due dates

Due input is `{ "value": "2026-10-22", "timezone": "America/Chicago" }`.
Timezone is optional and defaults to America/Chicago. Supported ISO values are
`2026`, `2026-10`, `2026-W43`, `2026-10-22`, and datetimes with hour, minute,
second or up to six fractional-second digits, optionally with a UTC offset.
Year/month/week/day values become overdue at the beginning of the following
local period. Timed values become overdue at the stated instant. The original
precision is retained alongside normalized UTC `starts_at` and `due_at`.

Timezone names are validated. Nonexistent local times are rejected. Ambiguous
local times require an explicit offset. Datetimes with an offset are interpreted
as instants in the chosen/default IANA timezone for recurring calendar schedules.

Item queries default to active items sorted by due time ascending, oldest overdue
first, undated last. Use `overdue_only=true` for only active overdue items.
`list_id` restricts a query to one list; omit it to query all lists. Completion and
cancellation are excluded from overdue queries even with `status=all`.

## Recurrence

Create a recurring item with a due date and either:

```json
{"mode":"calendar","rule":"FREQ=WEEKLY;BYDAY=MO,WE,FR"}
```

or:

```json
{"mode":"after_completion","every":3,"unit":"days"}
```

Calendar RRULEs support minute, hour, day, week, month and year frequencies,
intervals, weekday/month selectors, COUNT and UNTIL. The initial due date must
match the rule. Schedule resolution cannot be finer than due-date resolution.
No SECONDLY/BYSECOND rules are accepted. INTERVAL and completion intervals are
limited to 10,000; COUNT to 1,000,000; RRULE text to 4,096 characters. DTSTART,
RDATE, EXDATE and multi-line rule sets are not accepted.

Calendar schedules keep every missed valid occurrence. A worker creates all
elapsed occurrences plus the next upcoming one, in bounded atomic batches.
Its persisted cursor resumes after downtime without losing or duplicating items.
The worker normally checks every ten seconds and processes full catch-up batches
continuously. Reads do not trigger materialization. Month dates that do not exist
and DST gaps are skipped under calendar recurrence rules; ambiguous generated
times choose the first clock occurrence. Invalid calendar occurrences do not
consume COUNT. COUNT includes the first item. Calendar work continues whether
previous items are completed or still overdue.

Completion-based schedules create the next occurrence only after completing or
skipping the latest occurrence. Minutes/hours are elapsed time; larger units use
local calendar time, clamp month ends and advance DST gaps. Date-only schedules
retain date precision. Reopening and completing an older occurrence never creates
another successor. No elapsed-cycle backlog exists for completion-based schedules.

Cancelling a recurring item stops the entire series and cancels its active
siblings. `skip` cancels only that occurrence, records `skipped_at`, and continues
the series. Restoring an individual item does not restart a cancelled series;
restore the series explicitly. Calendar series resume their retained cursor,
including missed cycles while stopped; previously cancelled records remain
cancelled. Completion-based series restart from the resume time. A completed
series with COUNT/UNTIL exhausted remains active with `next_due: null`.

Template edits change the title, description and initial details of future
occurrences. Existing occurrence details remain independent. Schedule rules are
immutable in v1: cancel the old series and create a replacement to change its
calendar or interval. This preserves old dates and completion history.

## HTTP contract

All endpoints require a Farm service token for audience `urn:farm:service:tracker`
and `todos.read` or `todos.write`. Permissions and session validity are rechecked
with Farm on every request. No legacy-token, machine-token or development fallback
exists in the running service. The public health endpoint exposes no task data.

Responses are `{ "data": ... }`; errors are
`{ "error": { "code": "...", "message": "..." }, "request_id": "..." }`.
`GET /api/capabilities` advertises `farm.tracker/1`.

| Route | Methods | Purpose |
| --- | --- | --- |
| `/api/v1/lists` | GET, POST | Query/create lists |
| `/api/v1/lists/:id` | GET, PUT | Read/edit/cancel/restore list |
| `/api/v1/items` | GET, POST | Query/create items, including due queries |
| `/api/v1/items/:id` | GET, PUT | Read/edit/move/change status |
| `/api/v1/items/:id/details` | GET, POST | Paginate/add extra data |
| `/api/v1/items/:id/details/:detail_id` | PUT | Edit/cancel/restore detail |
| `/api/v1/items/:id/history` | GET | Paginate immutable history |
| `/api/v1/items/:id/skip` | POST | Skip one recurring occurrence |
| `/api/v1/recurrences` | GET | Query recurring series |
| `/api/v1/recurrences/:id` | GET, PUT | Read/edit template/cancel/restore series |

PUT is a guarded field update, not replacement. IDs are canonical UUID strings.
List endpoints return `{items, next_cursor}`; follow each opaque cursor with the
same query. Pages default to 10, maximum 50, with a 40 KiB record budget. Cursors
bind to database revision and query; concurrent changes return `cursor_conflict`
rather than silently dropping or duplicating data. Restart the query on conflict.
History is oldest first. Item ordering can also use `order_by=created_at`.
`q` searches list names and item titles/descriptions as literal substrings.

SQLite uses WAL, foreign keys, a busy timeout, transactional versioned schema
initialization and unique recurrence occurrence indexes. The existing recursive
dbops discovery and SQLite backup API cover the new database without changes.
